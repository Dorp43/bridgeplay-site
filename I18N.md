# Translation guide

The site ships in **7 languages**. This document is the contract.

| Code | Language | File |
|---|---|---|
| `en` | English (master + fallback) | `src/i18n/locales/en.ts` |
| `es` | Español | `src/i18n/locales/es.ts` |
| `de` | Deutsch | `src/i18n/locales/de.ts` |
| `fr` | Français | `src/i18n/locales/fr.ts` |
| `pt-BR` | Português (Brasil) | `src/i18n/locales/pt-BR.ts` |
| `ja` | 日本語 | `src/i18n/locales/ja.ts` |
| `zh-CN` | 简体中文 | `src/i18n/locales/zh-CN.ts` |

## The rule

**Every string a visitor can read lives in the dictionary.** A hard-coded
English string in a component is a bug, not a shortcut.

## Why you cannot forget

`src/i18n/types.ts` derives the shape from English:

```ts
export type Dictionary = typeof en;
```

Each translation declares `const es: Dictionary = { … }`. So the moment you add
a key to `en.ts`, **`tsc -b` fails in six files** until every language has it —
and `tsc -b` runs as part of `npm run build`. A half-translated site cannot
ship.

That failure is the feature. Do not defeat it by:

- widening `Dictionary` or using `Partial<>`
- marking keys optional with `?`
- adding an index signature
- writing a runtime `?? en.some.key` fallback

If a language genuinely has nothing to say for a key, repeat the English text
in that file explicitly. Then the omission is a visible decision in the diff
rather than an invisible hole.

## Workflow for any copy change

1. **Edit `en.ts` first.** It is the master; everything else follows it.
2. **Run `npx tsc -b`.** Six errors is correct. Zero errors means you edited a
   value, not a key — still translate it in all six files.
3. **Translate.** Match the site's voice: direct, plain, unhyped. Each locale
   file has a header comment describing its register (e.g. German and French
   use informal *du* / *tu* — the audience is Mac gamers, not enterprise
   buyers).
4. **Read it in the component**:
   ```tsx
   import { useI18n } from '../../i18n/useI18n';
   const { t } = useI18n();
   return <h2>{t.pricing.title}</h2>;
   ```
5. **`npm run build`** must pass.

## Conventions

**Interpolation is a function**, so translators can put the value where their
grammar needs it rather than being stuck with English word order:

```ts
memberSince: (date: string) => `Member since ${date}`,   // en
memberSince: (date: string) => `${date} から利用`,        // ja
```

**Lists are keyed objects, not arrays.** Features, FAQ entries, how-it-works
steps and compatibility items are objects keyed by a slug, and the component
holds an ordered array of those keys:

```ts
const FAQ_KEYS = ['whatIs', 'whichMacs', …] as const satisfies readonly (keyof typeof en.faq.items)[];
```

That gives two things an array cannot: a missing entry is a *type error* rather
than a silently short list, and the display order is fixed by the code so no
translation can reorder the FAQ by accident.

**Dates and numbers use the active locale.** `useI18n()` returns `bcp47` —
pass it to `toLocaleDateString` / `toLocaleString`. Never hard-code `'en-US'`.

**Prices stay in USD.** Paddle charges in USD and shows the authoritative
amount in its own overlay. A converted price rendered on the page would be a
number we cannot honour. Translate the surrounding sentence, keep `$6.99`.

## What deliberately stays in English

- **Legal document bodies** — `/terms`, `/privacy-policy`, `/refund-policy`,
  `/notices`. These are binding; a translation that disagrees with the original
  is worse than none. They carry `legal.englishOnlyNotice`, which *is*
  translated. Their tab titles are translated too (`t.meta.terms.title` etc.),
  and both `App.tsx` and the page's own `useDocumentMeta` read the same key —
  keep them in sync or the tab title visibly flips when the chunk lands.
- **Changelog release notes** — fetched from `changelog.json` at runtime. The
  page chrome around them is translated.
- **Product and technology names** — DirectDraw, DirectX, Rosetta 2, Apple
  Silicon, the anti-cheat vendor names, the product-name entries in
  `compatibility.specs.*.entries`, and every shell command. (The few prose
  entries in that spec sheet — "Hardware-accelerated 3D", "Bundled Windows
  runtime", "32-bit & 64-bit games" — *are* translated.)

## Names that must never appear in any locale file

The compatibility stack is never named or explained in visitor-facing copy — the
full rule is in [CLAUDE.md](CLAUDE.md). None of these may appear in **any** of
the seven locale files, in any script or transliteration:

> Wine · WineHQ · wined3d · WoW64 · Proton · DXVK · VKD3D · OpenGL · Metal (as a
> graphics API) · Themida · x87 · D3D12 · "built from source"

Write "its own Windows compatibility runtime" and state coverage as DirectDraw
and DirectX 8–11. A translator reaching for the old wording because it reads
more naturally in their language is exactly the failure this list exists to
stop. `tsc` cannot catch it — grep before you commit.

## Strings that are legal disclosures

Translate these carefully and **keep every element** — price, renewal cadence,
how to cancel, what happens to access afterwards. They are commented in `en.ts`.

- `pricing.footerSignedIn` / `pricing.footerSignedOut`
- `faq.items.cancel`
- `plans.*.features` (the "Billed $X every …" and "Cancel anytime …" bullets)

Shortening the wording is fine. Dropping a term is not.

## Adding a language

1. Add a row to `LOCALES` in `src/i18n/config.ts` (code, BCP-47 tag, endonym,
   2-letter chip, English name).
2. Create `src/i18n/locales/<code>.ts` typed `Dictionary`. Copying `en.ts` and
   translating in place is the fastest correct route.
3. Register the loader in `src/i18n/dictionaries.ts`.
4. `npm run build`.

Nothing else changes — the selector renders from `LOCALES`.

**Right-to-left is not supported yet.** Adding Hebrew or Arabic means auditing
every `*.module.css` for physical properties (`left`, `margin-right`,
`translateX`) and wiring `dir="rtl"`. Do not add an RTL language without doing
that work.

## How it fits together

```
src/i18n/
  config.ts         LOCALES, URL⇄locale mapping, detection, persistence
  types.ts          Dictionary = typeof en   ← the enforcement mechanism
  dictionaries.ts   en is static; the other six are lazy import() chunks
  useI18n.ts        context + hook  →  { locale, t, bcp47, ready, setLocale }
  I18nProvider.tsx  owns the active language
  locales/*.ts      the dictionaries
src/components/layout/LanguageSelector.tsx   the nav control
```

### The URL is the language

English lives at the root; every other language lives under its code:

```
/            /download            /ja            /ja/download
                                  /es/limitations   /zh-CN/notices
```

Each of those is a real, shareable, indexable address. The language is a
property of the URL, never of the visitor — two people opening `/ja/download`
see the same page.

- **Routing**: `main.tsx` reads the locale from `window.location.pathname`
  *before* React mounts and hands `localePrefix(locale)` to
  `<BrowserRouter basename>`. That is the whole trick: every existing
  `<Link to="/download">` resolves to `/ja/download` with no call-site change,
  and `useLocation().pathname` still reports `/download`, so path-dependent
  logic never had to learn about locales.
- **Raw `<a href="/#section">` anchors do NOT get the basename.** They must be
  `<Link to="/#section">`. The only legitimate bare `<a href="/…">` are the
  static files `/BridgePlay.dmg` and `/third-party-notices.md`, which are not
  routes and must never be prefixed.
- **English stays at the root on purpose.** It preserves existing URLs and their
  search history, and it keeps the three paths outside systems hard-code
  working: `/auth/action` (Firebase console action URL), `/app-checkout` (the
  Mac app's WKWebView and Paddle's `successUrl`), and the static files above.
  **Never move these behind a prefix.**
- **Detection and persistence**: `localStorage` under `bridgeplay.locale`
  records a choice. A visitor who has chosen a language and later lands on a
  bare English URL is redirected to their language — on the strength of the
  *stored choice only*, never on browser-language sniffing, so crawlers (which
  carry no localStorage) are never redirected and always index what they asked
  for.
- **First paint**: the locale is known synchronously from the URL. English is
  bundled; the others are lazy chunks (~13 kB gzip each), and `BootGate` in
  `main.tsx` holds the splash on `useI18n().ready` so nobody sees English flash
  into Japanese.
- **Switching** navigates rather than swapping state: `setLocale` does a
  `location.assign` to the same page under the new prefix, preserving path,
  query and hash. The router's basename is fixed for the life of the document,
  so a real navigation is the honest way to move between language roots — and
  it guarantees the URL, `<html lang>`, canonical, hreflang and `og:locale` all
  agree afterwards.
- **`<html lang>` and `og:locale`** follow the URL, written once the matching
  dictionary is on screen.

### SEO wiring — keep these four in agreement

`useDocumentMeta` emits a per-locale `canonical` plus eight `hreflang` links
(seven languages + `x-default`) on every route. Four things must agree exactly,
including trailing slashes, or they are worse than nothing:

1. the `canonical` for a page,
2. that page's own entry in its `hreflang` set,
3. the static `hreflang` block in `index.html` (home page only, for crawlers
   that do not run JS — `writeAlternates()` clears it once React takes over),
4. `public/sitemap.xml`, which lists every route × every language with
   reciprocal `xhtml:link` alternates.

**Adding a route means updating the sitemap.** Nothing enforces that
automatically.
